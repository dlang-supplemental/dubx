= dubx search: grouped registry search
:toc:

`dubx search <query>` asks code.dlang.org for packages, then groups the hits into status buckets with a short reason per package.
The old behaviour (pass through to `redub`/`dub search`) is still there with `--raw`.

== Usage

[source,shell]
----
dubx search yaml              # grouped, quiet output
dubx search yaml --verbose    # + repo, stars, downloads, open issues, README; streams the run log
dubx search yaml --json       # one JSON result document on stdout
dubx search yaml --no-cache   # skip the response cache
dubx search yaml --raw        # old passthrough: redub/dub search yaml
----

Results go to stdout. Warnings (for example a GitHub rate limit) and the `log:` path go to stderr.

[cols="1,3"]
|===
|Exit code |Meaning

|0 |Search ran (even if some lookups degraded).
|2 |Usage error (missing query, unknown option).
|3 |Network failure: the registry search itself failed.
|===

== Data sources

* `https://code.dlang.org/api/packages/search?q=` – the hit list.
* `/api/packages/<name>/info` – repository, every version with its date, README, dependencies.
* `/api/packages/<name>/stats` – downloads (total, monthly) and registry-side repo stars.
* GitHub `GET /repos/<owner>/<repo>` – 404 (repo gone), `archived`, `pushed_at`, stars, open issues. A redirect to another owner/name counts as "moved", not gone.
* GitHub `GET /repos/<owner>/<repo>/issues?state=all&per_page=10` – only for packages whose newest activity is older than `activeDays` (saves API quota).
* `raw.githubusercontent.com/<owner>/<repo>/HEAD/dub.sdl` (then `dub.json`) – a maintainer-declared `x:status`. dub drops unknown recipe keys, so the registry never stores this; raw file fetches do not count against the API limit.
* GitLab `GET /projects/<owner%2Frepo>` – archived, `last_activity_at`, stars, default branch. Bitbucket repos are not checked.
* Build status reported by the package's own CI, *for the exact release commit only* (top-level packages whose repo is reachable). The latest registry version's tag (`v<version>`, then `<version>`) is resolved to a commit SHA: GitHub `GET /repos/<o>/<r>/git/ref/tags/<tag>`, peeling annotated tags through `/git/tags/<sha>`; GitLab `GET /projects/<id>/repository/tags/<tag>`. Then GitHub check runs *and* combined status for that SHA (`/commits/<sha>/check-runs`, `/commits/<sha>/status`), or GitLab `/pipelines?sha=<sha>&per_page=1`. There is no branch fallback. A run from a push to `main` counts only if it ran on that same SHA.

`GH_TOKEN` (or `GITHUB_TOKEN`) is sent when set; it travels to `curl` on stdin, not on the command line.
Without a token GitHub allows 60 requests per hour. When the limit is hit dubx stops asking GitHub, judges the remaining packages from registry dates only, and says so on stderr.

HTTP goes through the system `curl` (Windows 10+, macOS, Linux ship it), 8 requests in parallel.
Responses (200 and 404 only) are cached for 60 minutes:

* Windows: `%LOCALAPPDATA%\dubx\cache\http`
* macOS: `~/Library/Caches/dubx/http`
* Linux: `$XDG_CACHE_HOME/dubx/http` (default `~/.cache/dubx/http`)

Next to the `http` folder, `repo-state.json` remembers, per repository, when dubx first saw it answer 404/451 (`firstGone`) and the last `x:status` read while it was reachable (`declaredStatus`). The entry is cleared when the repo answers again. It never expires; delete the file to reset.

Each run writes a JSON Lines log (`section`: `search`, `network`, `classify`) and keeps the newest 20:

* Windows: `%LOCALAPPDATA%\dubx\logs`
* macOS: `~/Library/Logs/dubx`
* Linux: `$XDG_STATE_HOME/dubx/logs` (default `~/.local/state/dubx/logs`)

== Why "Quiet" and not "Stale"

From the outside a stale package and a finished one look the same: no new releases.
Version numbers do not help either – `1.0` means "stable API" to one author and "first upload" to another.
So dubx only states hard facts as verdicts (repo 404, repo archived, the maintainer's own declared status) and keeps age-based groups neutral: *Quiet* means "old dates", and the reason shows those dates.

== Buckets and heuristics

All thresholds live in one place: `struct Thresholds` in `source/search_heuristics.d`.
`dubx search --json` echoes them under `thresholds`.

[cols="1,1,3"]
|===
|Threshold |Default |Used for

|`activeDays` |365 |Newest release, branch commit or repo push within this many days: *Active*.
|`quietDays` |1095 (3 years) |Between `activeDays` and this: *Slow but alive*. Older: *Quiet* (or *Finished* when the signals below say so).
|`issueSample` |10 |Recent issues (PRs excluded) sampled for responsiveness.
|`answeredPercent` |50 |Share of sampled issues closed or commented on to count as "answers issues".
|`minIssues` |3 |Fewer sampled issues than this: no responsiveness verdict.
|`goneGraceDays` |30 |How long a repo must keep answering 404/451 (counted from the first time dubx saw it) before it overrides a declared `x:status`.
|`wrapperDescriptionPattern` |`\b(bindings?\|wrappers?\|wraps\|port of\|interface to\|binding for)\b` |Description words that mark a wrapper.
|===

Rules, first match wins:

. *Repo gone or archived* (`gone`) – the repo is archived, or the host says 404/451. A 404 with no declared status counts at once. A package with a declared `x:status` (the current recipe, or the one remembered in `repo-state.json`) keeps its declared bucket for `goneGraceDays`, with `repo unreachable since <date>` in the reason; after that the 404 wins. Repos get renamed, made private for a day, or restored.
. *Declared status* – the maintainer's `x:status` beats every heuristic and is shown first in the reason:
** `complete`, `maintenance-only` → *Finished or maintenance-only* (`finished`)
** `deprecated`, `unmaintained` → *Declared deprecated or unmaintained* (`unmaintained`)
** `experimental`, `alpha`, `beta`, `stable` → *Active* (`active`)
. *Wrapper or subpackage* (`wrapper`) – name contains `:`; or a dependency of the newest release is another package in the same result set (own subpackages ignored); or the description matches `wrapperDescriptionPattern`.
. *Active* (`active`) – newest activity ≤ `activeDays`.
. *Slow but alive* (`slow`) – newest activity ≤ `quietDays`.
. *Finished or maintenance-only* (`finished`) – older than that, but it answers issues *or* its own CI passes, and neither its CI fails nor it is known not to build.
. *Quiet* (`quiet`) – older than that, nothing else known. A fact, not a verdict.
. *Unknown* (`unknown`) – no registry info at all.

"Newest activity" is the latest of: newest tagged release date, newest `~branch` version date in the registry, and the repo's `pushed_at` / `last_activity_at`.

=== Build status (reported by the package's own CI)

The reason shows `CI passing on v2.2.0 (2025-10)`. `--verbose` adds the source (`github-checks`, `github-status`, `gitlab-pipeline`, joined with `+` when both agree), the tag with the short SHA (`v2.2.0 @ 86e74d6`) and a link. When check runs and commit status disagree, failing beats pending beats passing. The date matters: a green result from years ago says the package built with the compilers of that time. dubx does not run builds; the result is whatever the maintainer's CI reported, so it is evidence, not proof.

With no release tag, or no CI results on the tagged commit, there is no status: `--verbose` prints `CI: none for release (<reason>)` and the default output only counts such packages in a footer. Either way dubx links to link:ci-status-for-releases.adoc[Link your CI to your release] (`ciHelpUrl`). It never counts as passing or failing.

The link is an OSC 8 terminal hyperlink when stdout is a terminal known to render it (Windows Terminal, VS Code, iTerm2, WezTerm, kitty, foot, Ghostty, Konsole, VTE ≥ 0.50); otherwise, including when piped, dubx prints the plain URL. `DUBX_NO_HYPERLINKS=1` forces the plain URL.

* check runs: any `failure`, `timed_out`, `action_required` or `startup_failure` → failing; any run not completed → pending; otherwise passing.
* combined status: `success` → passing, `pending` → pending, `failure`/`error` → failing; zero statuses → unknown.
* GitLab: `success`, `failed`, running-like states → pending; `canceled`/`skipped`/`manual` → unknown.

=== Dependents

`used by N of these results` counts only packages *in the same search results* whose newest release depends on this one (own subpackages excluded). code.dlang.org has no reverse-dependency API, and computing a registry-wide count would mean fetching every package, so dubx does not. The human output prints a footnote, and the JSON says `"dependentsScope": "search-results"`.

=== Signals kept as hooks

* `buildsWithCurrent` – does it still build with *current* DMD/LDC? Only a registry-side build (see the upstream proposal) can say. Stays `null`.

=== JSON fields added in 0.5.0

* `dependentsScope`: always `"search-results"`.
* per package `ci`: `{state: passing|failing|pending, source, tag, sha, date, url, reportedBy: "package CI"}`, or `null` when there is no result for the release commit; then `ciReason` says why and `ciHelpUrl` links the how-to.
* per package `dependents`: `{scope: "search-results", count, names}` (was a `-1` hook).
* per package `repoGoneSince`: first date dubx saw the repo answer 404/451, or `null`.
* `thresholds.goneGraceDays`.

== Commands vs. package names

`dubx search` (and every other built-in) always runs dubx's own code. dubx never treats an unknown first word as a package to fetch and run (older releases forwarded unknown words to redub, which did exactly that: `dubx search yaml` on 0.3.x fetched a package called `search`). An unknown word prints a hint and exits 2:

[source]
----
dubx: unknown command 'serch'. Did you mean 'dubx search'?
  dubx does not fetch or run a package from a bare name.
  To run a registry package named 'serch': dubx dub run serch
----

== Declaring a status in your own package

dub ignores unknown recipe keys, so this is safe to add today:

[source,sdl]
----
x:status "complete"
----

[source,json]
----
{ "x:status": "complete" }
----

`complete` is the value that tells *finished* apart from *quiet*. See link:upstream/dub-registry-grouped-search.md[the upstream proposal] for making this a real recipe field.
