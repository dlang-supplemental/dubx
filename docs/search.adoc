= dubx search: grouped registry search
:toc:

`dubx search <query>` asks code.dlang.org for packages, then groups the hits into status buckets with a short reason per package.
The old behaviour (pass through to `redub`/`dub search`) is still there with `--raw`.

== Usage

[source,shell]
----
dubx search yaml              # grouped, quiet output
dubx search yaml --verbose    # + repo, stars, downloads, open issues, README; streams the run log
dubx search yaml --json       # one JSON result document on stdout
dubx search yaml --no-cache   # skip the response cache
dubx search yaml --raw        # old passthrough: redub/dub search yaml
----

Results go to stdout. Warnings (for example a GitHub rate limit) and the `log:` path go to stderr.

[cols="1,3"]
|===
|Exit code |Meaning

|0 |Search ran (even if some lookups degraded).
|2 |Usage error (missing query, unknown option).
|3 |Network failure: the registry search itself failed.
|===

== Data sources

* `https://code.dlang.org/api/packages/search?q=` – the hit list.
* `/api/packages/<name>/info` – repository, every version with its date, README, dependencies.
* `/api/packages/<name>/stats` – downloads (total, monthly) and registry-side repo stars.
* GitHub `GET /repos/<owner>/<repo>` – 404 (repo gone), `archived`, `pushed_at`, stars, open issues. A redirect to another owner/name counts as "moved", not gone.
* GitHub `GET /repos/<owner>/<repo>/issues?state=all&per_page=10` – only for packages whose newest activity is older than `activeDays` (saves API quota).
* `raw.githubusercontent.com/<owner>/<repo>/HEAD/dub.sdl` (then `dub.json`) – a maintainer-declared `x:status`. dub drops unknown recipe keys, so the registry never stores this; raw file fetches do not count against the API limit.
* GitLab `GET /projects/<owner%2Frepo>` – archived, `last_activity_at`, stars. Bitbucket repos are not checked.

`GH_TOKEN` (or `GITHUB_TOKEN`) is sent when set; it travels to `curl` on stdin, not on the command line.
Without a token GitHub allows 60 requests per hour. When the limit is hit dubx stops asking GitHub, judges the remaining packages from registry dates only, and says so on stderr.

HTTP goes through the system `curl` (Windows 10+, macOS, Linux ship it), 8 requests in parallel.
Responses (200 and 404 only) are cached for 60 minutes:

* Windows: `%LOCALAPPDATA%\dubx\cache\http`
* macOS: `~/Library/Caches/dubx/http`
* Linux: `$XDG_CACHE_HOME/dubx/http` (default `~/.cache/dubx/http`)

Each run writes a JSON Lines log (`section`: `search`, `network`, `classify`) and keeps the newest 20:

* Windows: `%LOCALAPPDATA%\dubx\logs`
* macOS: `~/Library/Logs/dubx`
* Linux: `$XDG_STATE_HOME/dubx/logs` (default `~/.local/state/dubx/logs`)

== Why "Quiet" and not "Stale"

From the outside a stale package and a finished one look the same: no new releases.
Version numbers do not help either – `1.0` means "stable API" to one author and "first upload" to another.
So dubx only states hard facts as verdicts (repo 404, repo archived, the maintainer's own declared status) and keeps age-based groups neutral: *Quiet* means "old dates", and the reason shows those dates.

== Buckets and heuristics

All thresholds live in one place: `struct Thresholds` in `source/search_heuristics.d`.
`dubx search --json` echoes them under `thresholds`.

[cols="1,1,3"]
|===
|Threshold |Default |Used for

|`activeDays` |365 |Newest release, branch commit or repo push within this many days: *Active*.
|`quietDays` |1095 (3 years) |Between `activeDays` and this: *Slow but alive*. Older: *Quiet* (or *Finished* when the signals below say so).
|`issueSample` |10 |Recent issues (PRs excluded) sampled for responsiveness.
|`answeredPercent` |50 |Share of sampled issues closed or commented on to count as "answers issues".
|`minIssues` |3 |Fewer sampled issues than this: no responsiveness verdict.
|`wrapperDescriptionPattern` |`\b(bindings?\|wrappers?\|wraps\|port of\|interface to\|binding for)\b` |Description words that mark a wrapper.
|===

Rules, first match wins:

. *Repo gone or archived* (`gone`) – repository host says 404/451, or the repo is archived. Hard facts.
. *Declared status* – the maintainer's `x:status` beats every heuristic and is shown first in the reason:
** `complete`, `maintenance-only` → *Finished or maintenance-only* (`finished`)
** `deprecated`, `unmaintained` → *Declared deprecated or unmaintained* (`unmaintained`)
** `experimental`, `alpha`, `beta`, `stable` → *Active* (`active`)
. *Wrapper or subpackage* (`wrapper`) – name contains `:`; or a dependency of the newest release is another package in the same result set (own subpackages ignored); or the description matches `wrapperDescriptionPattern`.
. *Active* (`active`) – newest activity ≤ `activeDays`.
. *Slow but alive* (`slow`) – newest activity ≤ `quietDays`.
. *Finished or maintenance-only* (`finished`) – older than that, but it answers issues and is not known to fail to build.
. *Quiet* (`quiet`) – older than that, nothing else known. A fact, not a verdict.
. *Unknown* (`unknown`) – no registry info at all.

"Newest activity" is the latest of: newest tagged release date, newest `~branch` version date in the registry, and the repo's `pushed_at` / `last_activity_at`.

=== Signals kept as hooks

These are in `Facts` and the JSON output but have no cheap source yet, so they stay unknown (`null` / `-1`):

* `buildsWithCurrent` – does it still build with current DMD/LDC? The strongest liveness signal. Neither the registry nor GitHub exposes it today; a registry-side build bot would fill it (see the upstream proposal).
* `dependents` – how many packages depend on it and how recent their releases are. The registry has no reverse-dependency endpoint.

  ...
----

== Declaring a status in your own package

dub ignores unknown recipe keys, so this is safe to add today:

[source,sdl]
----
x:status "complete"
----

[source,json]
----
{ "x:status": "complete" }
----

`complete` is the value that tells *finished* apart from *quiet*. See link:upstream/dub-registry-grouped-search.md[the upstream proposal] for making this a real recipe field.
